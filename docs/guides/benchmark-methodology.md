# Benchmark Methodology

This document explains exactly how RadixIP's performance numbers are
produced, so they can be reproduced, audited, or challenged. Any number
quoted in the README should be traceable back to this process — if it
isn't, treat it as unverified.

## Dataset generation

Benchmarks run against a synthetic but structurally realistic dataset,
generated by `scripts/generate_mock_data.py`:

- **Subnets**: a configurable number (default 10,000) of randomly generated
  CIDR blocks, with mask lengths mixed across `/8`, `/16`, and `/24` to
  avoid an artificially uniform tree shape. Each subnet is tagged with mock
  geo/ISP metadata for realism, though the metadata content doesn't affect
  lookup performance.
- **Lookups**: a configurable number (default 100,000) of IP addresses,
  generated as a mix of:
  - **Hits** (default 80%): addresses drawn from *inside* one of the
    generated subnets, so the lookup should resolve to a match.
  - **Misses** (default 20%): addresses outside any inserted subnet, to
    exercise the full-depth traversal (or early termination) path that
    occurs when nothing matches.
  - The final list is shuffled, so hits and misses are interleaved
    unpredictably — this avoids the CPU branch predictor learning a
    pattern that wouldn't hold under real traffic.

This dataset is written once to `benchmarks/data/mock_network_data.json`
and reused by both the Go and Rust benchmark suites, so the two languages
are compared against identical input.

## Why generate data instead of hand-picking IPs

A small, fixed set of test IPs would fit entirely in L1/L2 cache regardless
of the data structure, producing unrealistically fast and misleading
numbers for both the hashmap baseline and the radix tree. A larger,
randomized dataset forces genuine cache pressure and gives a more honest
picture of steady-state performance. See
[cache-locality.md](./cache-locality.md) for why this distinction matters.

## Go benchmarks

Run via the standard library's `testing` package:

```bash
cd radixip-go   # or lib/go, depending on current layout
go test -bench=. -benchmem ./...
```

- Dataset loading happens *before* `b.ResetTimer()`, so parsing/setup cost
  isn't counted in the reported latency.
- `-benchmem` reports allocations per operation (`B/op`, `allocs/op`),
  which is how the "zero allocation" claims are verified — not asserted.
- `b.RunParallel` is used to exercise the lock-free read path under
  concurrent access, matching the intended production usage pattern.

## Rust benchmarks

Run via [Criterion](https://github.com/bheisler/criterion.rs):

```bash
cd radixip-rs   # or lib/rust
cargo bench
```

Criterion handles warm-up iterations, statistical outlier detection, and
produces confidence intervals rather than a single point estimate — the
headline "~12ns" figure quoted elsewhere refers to Criterion's reported
mean, and the full distribution (including variance) is available in
Criterion's generated HTML report, not just the single number.

## What "reference (hashmap)" means

Where a hashmap baseline is quoted for comparison, it refers to a simple
exact-match hashmap over the same dataset's individual IPs (not subnets),
included specifically to illustrate the cache-locality argument made in
[cache-locality.md](./cache-locality.md) — it is not a claim that a hashmap
is a reasonable alternative for LPM, since a plain hashmap can't perform
prefix matching at all. Treat it as an illustration of access-pattern cost,
not a fair like-for-like competitor.

## Continuous benchmarking (CI)

A GitHub Actions workflow (`.github/workflows/bench.yml`) regenerates the
dataset and runs both benchmark suites on every push to `main`, uploading
the raw output as a build artifact. This exists so that:

- Numbers in the README can be checked against an independently generated
  run, not just numbers pasted in by hand.
- Performance regressions are visible in CI history over time, rather than
  only being noticed anecdotally.

To audit a specific commit's numbers, pull the corresponding workflow run
from the Actions tab and download its artifact rather than trusting the
README figure in isolation — hardware differences between your machine and
the CI runner mean *absolute* numbers won't match exactly, but relative
comparisons (Go vs Rust vs hashmap) should hold.

## Limitations and honest caveats

- These are **microbenchmarks** of the lookup function in isolation, not
  end-to-end measurements of a real proxy or gateway under production
  traffic. Real-world latency will include TLS, syscalls, connection
  pooling, etc. — RadixIP's contribution to total request latency is the
  microbenchmark figure, not a replacement for it.
- Numbers are specific to the CI runner's hardware (or your local machine,
  if you run it yourself) and will vary across CPUs, especially around
  cache sizes and memory latency.
- Cache hit-rate claims for any specific traffic pattern (e.g. IPv6 `/64`
  aggregation) depend entirely on the real distribution of that traffic.
  This methodology measures raw lookup latency, not cache hit rate for a
  particular workload — if you need a hit-rate figure for your own traffic,
  measure it against your own data rather than extrapolating from the
  synthetic 80/20 split used here.
